# Portfolio site

Vite + strict TypeScript, no framework. "Departures": ten places, one painting per place filling the whole window, a hard slat cut between them, and the board of places in a drawer; see README.md for the map. Every place is built like the opening shot of the summit: the painting, a kicker, a big name low in the frame, one line and its buttons; the longer text is behind "Read". The board slides in from the left when the small tag in the top corner (`07/09  Kyoto  LIVE  ↑ ↓ to travel`) is pressed; on phones the same button is the bar at the bottom and the board is a sheet. The page opens on the summit with not even the tag (it comes with the first step); the paintings move (WebGL, `src/living/`) and each place has a synthesised sound (`src/sound/`), behind two corner switches. On phones the board is a sheet raised from the bar. The pictures are paintings (they used to be photographs, which is why modules and comments still say photo: `worlds/photos.ts` and the rest keep their names).

## Commands

- `npm run dev` — dev server (no API unless `.env` sets `VITE_API_URL`)
- `npm run check` — lint + typecheck + unit tests + build. Run before every commit.
- `npm run test:e2e` — Playwright smoke suite against the real build, served from `/` as on kekaisik.dev (rebuild first if a preview server is already running on 4173: it is reused), plus the sound check against the dev server on 5174. Locally it asks Chromium for the real GPU (`--use-angle=gl`); on a machine without one the tests that watch the paintings move skip themselves.
- `npm run format` — prettier
- `npm run worlds -- <folder>` — make `public/worlds/*.webp` (landscape + upright crop per world) and `src/worlds/placeholders.json` from the source paintings, which must be in the folder under the names in the table at the top of `scripts/make-worlds.ts` (needs ffmpeg with libwebp). The sources live outside the repo, in `../reference/painted-sources/` (1536x1024 PNGs, made by `gen.sh` there with Codex's image tool: one prompt per place); don't edit or regenerate them as part of a code change. Run after changing a painting or a world's `focus` in `src/worlds/looks.ts`; commit the results. A unit test caps every file's size.
- `npm run video -- <file> <slug>` — compress a video into `public/videos/<slug>.mp4` (H.264, 720p, at most 2 MB). Every video goes in this way, never as a raw copy: recorders write HEVC, which Firefox can't play, and a unit test fails above 2 MB.

## Conventions

- All text lives in `src/content/` (projects, the board's places and status words, messages). Never hard-code copy in DOM code or in `index.html`: the shell has `{{slots}}` filled by `content/render.ts` at build time.
- One project = one entry in `content/projects.ts` + its place in `content/places.ts` + its look in `worlds/looks.ts` + its scene in `living/scenes.ts` + its sound in `sound/recipe.ts` + its painting (`scripts/make-worlds.ts` maps source file to world id). Unit tests fail until all six exist. Slugs are public (links, photo and video names, API growth keys): don't rename.
- The painting is the hero and fills the window. Words stand low left by default, top left only where the lower left of that painting holds the subject (`looks.ts`: `at`, `width`, `x`, `atTall`). Behind them only a halo around the letters and a soft ellipse of shade that fades out before its own edge (`shade` sets how dark, as light as AA contrast allows): never a box, a smear or a scrim. Only the kicker, name, line and buttons stand on the painting; longer text goes behind "Read". After changing a look or a text, look at screenshots of that world at 1440x900, 1366x680, 390x844 and 320x568, and check the contrast of the letters against what is behind them.
- Performance rules (the previous site lagged): in CSS animate only `transform` and `opacity`; no blend modes, filters, backdrop-filter or clip-path on big layers; at most three photos mounted (`worlds/photos.ts`); no scroll smoothing: travel is one step per gesture. A photo is shown only after `img.decode()`. There is one frame loop (`lib/ticker.ts`); everything that draws subscribes to it and it rests in a hidden tab, under a cover (video, sheet, raised index) and with the motion switch off. The living photo must stay GPU work: per frame the main thread sets a few uniforms and makes one draw call (budget: p95 frame under 20 ms at 1440x900 and 390x844, idle and travelling; main thread well under 1 ms a frame). Never: layered parallax, cursor-reactive effects, animated CSS filters.
- A spot (a thing to open inside a painting: a project's video or its "try it") is data too: `worlds/spots.ts` (at most two per world, one of each, in the landscape painting's 0..1 coordinates; pure, unit-tested), its label is the project's `spot` in `content/projects.ts` (video) or the try's `spot` in `content/tries.ts`, and `worlds/spot-view.ts` puts it on its object with the cover maths and hides it (keeping the Watch or Try it button) where it would be cut off or stand on the words, the switches, the tag or the other spot. Its ring breathes with transform/opacity only and stands still with the motion switch off or reduced motion. README "Add a spot" is the how-to.
- A reaction (one unlabelled object per place that answers a press: `worlds/reactions.ts`, data built from three effects: `flare`, `burst`, `streak`; its name is the place's `react` in `content/places.ts`) is an invisible real button the size of the object, placed by `worlds/react-view.ts` with the cover maths and left out where it would crowd the words, a spot, the switches or the tag, and gone with the motion switch off. Effects animate opacity/transform only (flares and streaks as elements in the `.spots` layer, bursts on the ambient canvas, which leaves the frame loop again when they are over). No hover effect, nothing that follows the cursor. README "Add a reaction" is the how-to.
- A try (`src/try/`) is a small pure state machine per kind (`kana`, `fight`, `call`, `pick`) plus its words and data in `content/tries.ts`; the shared card (`try/panel.ts`) only draws the machine's view and must stay free of behaviour worth testing. Keep each try to 5-15 seconds of plain choices (Kaisar dislikes drag-to-reveal, knobs, cursor effects and anything that loads the head); a private project's try is marked as an example and names no client, number or currency. Dice come from `lib/random.ts`. Links only to pages you have opened. README "Add a try-it" is the how-to.
- What moves in a painting is data (`living/scenes.ts`), authored by looking at the painting with a grid over it; README "Make a place move" is the how-to. Nothing is pushed by wind (Kaisar: cloud, grass, leaves or fog carried across the picture read as the painting being dragged): `flow` is for running water only, wind lives in the particles (`looks.ts` ambient). Regions stop short of solid things, moves stay small (unit tests cap them), and the canvas must stay transparent where nothing moves so the `<img>` is what you see. After changing a scene, look at two frames two seconds apart and their difference.
- Sound: off by default, never an `AudioContext` before a gesture (a browser warning in the console is a failed test), nothing downloaded: recipes in `sound/recipe.ts`, built by `sound/engine.ts` on any `BaseAudioContext`. Nobody has listened to it through the tests: the sound check only proves each place is audible, quiet (peak under 0.9), unclipped and centred.
- Words must be readable about 300 ms after a key: the cut is 300 ms (`worlds/slats.ts`), and nothing may delay the words after it lands.
- Modules that touch the DOM at import (`lib/media.ts` and whatever imports it) cannot be unit-tested in jsdom; keep logic worth testing in DOM-free modules (`content/*`, `worlds/cover.ts`, `slats.ts`, `looks.ts`, `spots.ts`, `living/raster.ts`, `noise.ts`, `scenes.ts`, `sound/recipe.ts`, `samples.ts`, `switches/prefs.ts`, `travel/gesture.ts`, `board/scramble.ts`, `nav/routing.ts`, `note/machine.ts`, `try/kana.ts`, `fight.ts`, `call.ts`, `pick.ts`, `run.ts`, `night/today-text.ts`, `lantern-math.ts`, `worlds/reactions.ts`, `video/files.ts`, `lib/queries.ts`, `lib/random.ts`).
- Narrow layout = phones and upright tablets: `NARROW_QUERY`/`TALL_QUERY` in `lib/queries.ts` and the media queries in `styles/narrow.css` must agree (a unit test checks).
- No `any`, no non-null assertions, no bare `catch`: catch the specific error type and rethrow the rest. API failures are values (`ApiResult`), handled per endpoint; responses are checked with Zod.
- Never call the production API from tests or while verifying. The e2e suite fails on any request that leaves 127.0.0.1.
- CSS: one file per concern in `src/styles/`, colours and type from `tokens.css`. `narrow.css` then `motion.css` (reduced motion) must stay after the files they override.
- Accessibility is part of parity: skip link, keyboard travel (the tag `#bar` is a button with `aria-expanded`/`aria-controls`; it is a Tab stop during the opening shot too, and focus reaching it is a first step; it opens the board with focus on the current row, which is the board's one Tab stop; Esc, a press outside or choosing a row closes it, and focus returns to the tag, or goes on to the new world's name after choosing a row on a wide screen; closed, the board is `inert`), focus moved to the new world's name, `aria-live` arrival line, modal dialogs for the video / Read / the note / a try (Esc, focus return; a try's presses are told through `aria-live`), 44 px targets, the corner switches are toggle buttons (`aria-pressed`, off = struck through, not colour alone), reduced motion = instant cuts and the motion switch starts off.
- The opening shot (`opening/opening.ts`, `styles/opening.css`): the `opening` class is set before first paint in `index.html` only when there is no `#link`; it only hides the tag until the first step. The stage, `main`, `#cut`, the player and the sheets always fill the window: nothing changes shape. The drawer moves by transform only (`board.css`, `narrow.css`), and not at all under reduced motion.
